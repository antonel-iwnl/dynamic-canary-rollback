# Dynamic CI/CD Canary Rollback Using Unsupervised Machine Learning (`IsolationForest`)

## 1. Overview of the Software Engineering Problem Addressed
In modern Continuous Integration and Continuous Deployment (CI/CD) pipelines, **Canary Releases** mitigate deployment risk by routing a small subset of live user traffic (e.g., 20%) to a newly deployed version (`canary`) while the majority of traffic (80%) continues to be served by the proven production version (`stable`).

Traditionally, canary health checks rely on **static, hand-crafted threshold rules** (e.g., `CPU > 80%` or `Latency > 500ms`). However, static thresholds suffer from two critical software engineering limitations:
1. **Alert Fatigue & False Positives**: Normal traffic spikes can breach rigid single-metric thresholds even when the release is healthy.
2. **Missed Multi-Dimensional Regressions**: Subtle performance regressions—such as a gradual memory leak paired with elevated tail latency and moderate CPU contention—often remain below individual static alarms until the container crashes in production.

This project automates **CI/CD Canary Health Monitoring and Rollback** using an unsupervised **Isolation Forest** anomaly detection pipeline that learns the multivariate baseline behavior of the `stable` release directly from live Prometheus telemetry and automatically triggers a rollback when anomalous degradation is detected on the `canary` release.

## 2. Data Collection Methodology
To satisfy both **real-world generalization** and **live software engineering validation**, a two-phase data collection strategy was designed:

### Phase A: Offline Real-World Benchmark (Server Machine Dataset — SMD)
- **Source**: Publicly available **Server Machine Dataset (`machine-1-1.txt`)** in `canaryrollbackML/smd_analysis.ipynb`.
- **Composition**: `28,479` baseline training time steps and `28,479` labeled test time steps across `38` multivariate server performance metrics (CPU load, memory footprint, network I/O, disk utilization, etc.).
- **Purpose**: Proves that the `IsolationForest` algorithm detects real-world, multivariate server anomalies prior to building the live microservice infrastructure.

### Phase B: Live Containerized Microservice Telemetry (`collected_metrics.csv`)
- **Source**: Custom containerized FastAPI microservice ([api/main.py](api/main.py)) instrumented with `prometheus_client` and `psutil`, scraped at 2-second intervals via `/metrics` under continuous synthetic load generated by **Locust** ([load_tester/locustfile.py](load_tester/locustfile.py), 50 concurrent users with an 80/20 stable-to-canary traffic split).
- **Features Collected**:
  1. `cpu_usage` (`app_cpu_usage_percent`): Process & system CPU utilization (%).
  2. `memory_usage` (`app_memory_usage_mb`): Resident Set Size (RSS) memory usage (MB).
  3. `request_latency` (`app_request_latency_seconds`): End-to-end HTTP `GET /` request processing duration (seconds).
- **Dataset Size**: `530` live telemetry observations (`500` healthy baseline samples from `VERSION=stable` on port `8000` followed by `30` canary samples from `VERSION=canary_poisoned` on port `8001`).

| Telemetry Metric | Stable Baseline (`n = 500`, Mean ± SD) | Poisoned Canary (`n = 30`, Mean ± SD) | Observed Shift |
| :--- | :---: | :---: | :---: |
| **CPU Usage (%)** | `9.72% ± 0.71%` | `67.53% ± 5.93%` | `+57.81%` (~6.9×) |
| **Memory Usage (MB)** | `44.15 MB ± 0.02 MB` | `209.69 MB ± 1.43 MB` | `+165.54 MB` (~4.7×) |

## 3. Machine Learning Approach & Implementation Details

### 3.1 Rationale for Choosing Unsupervised `IsolationForest`
- **Absence of Labeled Failures in CI/CD**: In production software engineering, teams have abundant telemetry from the healthy `stable` release, but zero labeled examples of the specific bug a future `canary` commit might introduce. Supervised classifiers require historical failure labels and fail on novel regressions; **unsupervised anomaly detection** requires only healthy baseline data.
- **Computational Efficiency ($O(n \log \psi)$)**: `IsolationForest` isolates anomalies by randomly partitioning features into binary trees (`n_estimators = 100`, subsample size $\psi = 256$). Anomalous canary states lie far from dense normal clusters and are isolated near the root of the trees (short average path length $E(h(x))$), yielding negative decision scores $s(x) < 0$ and prediction `-1` in sub-millisecond inference time suitable for real-time CI/CD polling.

### 3.2 Implementation Pipeline ([ml_monitor/monitor.py](ml_monitor/monitor.py))
1. **Data Preprocessing (`preprocess_data()`)**:
   - Extracts the 3 telemetry features (`cpu_usage`, `memory_usage`, `request_latency`).
   - Sanitizes missing or infinite readings using forward-fill (`ffill`) and median imputation, and clips non-physical negative values to `0.0`.
   - Applies **`StandardScaler` ($z$-score normalization)** inside a `scikit-learn` `Pipeline` so features measured on incompatible physical units (`%`, `MB`, and `seconds`) are standardized to zero mean and unit variance ($\mu = 0, \sigma = 1$).
2. **Model Training (`train_baseline()`)**:
   - Fits the `Pipeline([("scaler", StandardScaler()), ("isolation_forest", IsolationForest(n_estimators=100, max_samples="auto", contamination=0.02, random_state=42))])` on the `500` healthy `stable` observations.
   - Using `500` baseline samples allows each of the `100` trees to draw a distinct random bootstrap subsample of `256` observations, reducing ensemble variance and capturing steady-state Locust traffic fluctuations.
3. **Real-Time Canary Monitoring & Debounced Rollback (`monitor_canary()`)**:
   - Evaluates each incoming canary data point via `model.predict()` and `model.decision_function()`.
   - Prints `[ALERT] ... -> ANOMALY DETECTED: INITIATING ROLLBACK` upon anomaly detection (`prediction == -1`).
   - Enforces a **Consecutive Anomaly Debounce Window (`rollback_threshold = 3` by default)** before halting the deployment, preventing transient single-tick network jitter from causing an unnecessary production rollback.

## 4. Validation Results & System Effectiveness

### 4.1 Offline Validation on Real-World SMD Dataset (`canaryrollbackML/smd_analysis.ipynb`)
- Validated on `machine-1-1` (`28,479` test points across 38 metrics).
- Achieved **Precision = `0.297`**, **Recall = `0.409`**, **F1-Score = `0.344`** on raw point-wise 38-dimensional server telemetry, successfully flagging the major real-world incident spikes across the time series.

### 4.2 Live CI/CD Pipeline Validation ([collected_metrics.csv](collected_metrics.csv) & [ml_monitor/evaluate_model.py](ml_monitor/evaluate_model.py))
When validated in the live Dockerized environment across `530` telemetry samples (`500` stable + `30` canary):
- **Precision**: `1.0000` (with consecutive-window debouncing) / `0.7500` (at strict `contamination = 0.02` baseline calibration)
- **Recall (Sensitivity)**: `1.0000` (`30 / 30` poisoned canary points immediately flagged as `-1` with decision score $s(x) = -0.1400$)
- **F1-Score**: `1.0000` (deployment-level rollback accuracy)
- **Time-to-Rollback**: `6.0 seconds` (`3` consecutive 2-second polling intervals after switching to canary)
- **Visual Validation**: See [ml_monitor/live_validation_results.png](ml_monitor/live_validation_results.png) for the 4-panel time-series visualization of CPU, Memory, Request Latency, and `IsolationForest` decision scores.

## 5. Suggestions for Future Improvements & Further Research
1. **Multivariate Rolling-Window Feature Engineering**: Augment point-in-time metrics with rolling 30-second means, standard deviations, and first-order derivatives ($\Delta\text{Memory}/\Delta t$) to detect slow, low-slope memory leaks even earlier.
2. **Additional Golden Signals**: Incorporate HTTP `5xx` error rates and `p95`/`p99` histogram latency quantiles (`app_request_duration_seconds_bucket`) alongside CPU and RSS memory.
3. **Automated Traffic-Router Integration**: Connect the `monitor_canary()` rollback trigger directly to an **NGINX / Envoy / Kubernetes Argo Rollouts webhook** to automatically shift the 20% canary weight back to 0% without human intervention.
4. **Adaptive Concept-Drift Retraining**: Periodically retrain the baseline `IsolationForest` using a sliding window of recent `stable` telemetry to adapt to diurnal traffic patterns (day vs. night load).
